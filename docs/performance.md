# 性能：Python 侧到底要花多少时间

一句话：**读缓存是微秒级（`status()` 4.3 µs），动作是毫秒级（≥20 ms），而后者由后端控制周期决定，不是 SDK 的开销。**

## 口径（先说清，否则数字没意义）

计时区间 = **一次完整用户写法**：`robot.status().status()`、`robot.perception().laser_scan()`、
`robot.motion().move_to_joint_positions(goal)`。**含** pybind 边界、属性访问、C++ 里的加锁与投影、数据拷贝；
动作那两行的 `goal` 构造在区间**外**（准备数据不算"调用"）。**不含**并发/吞吐、跨机 DDS、Nav2/MoveIt/真硬件耗时。

**为什么必须含属性访问**：不含（把绑定方法预先取好）数字会好看 1.5–2.5 µs，但那是**用户不会那样写**的数。
同进程一次性对照（n=20000，微秒）：

| 写法 | p50 | p95 |
|---|---|---|
| 只取访问器 `robot.status()`（在测量壳里调） | 1.13 | 1.28 |
| 预先绑定 `status_api.status()` | 1.77 | 2.09 |
| **用户真实写法** `robot.status().status()` | 3.20 | 12.18 |

⇒ 属性访问每次约 **0.4 µs 起**，而且每轮多分配一个 Python 对象，**长尾明显变重**（p95 2.1 → 12.2 µs）。

## 结果（统一口径，p50 / p95 / p99，微秒）

| 项目 | n | p50 | p95 | p99 | 说明 |
|---|---|---|---|---|---|
| `has_status()` | 20000 | 3.06 | 4.77 | 7.40 | pybind 地板（含属性访问） |
| `status()` | 20000 | 4.29 | 4.89 | 9.70 | 地板 + 加锁 + 投影成 dict（6 字段） |
| `joint_states()` | 20000 | 5.31 | 6.11 | 13.96 | 3 个数组（6 关节） |
| `laser_scan()` | 5000 | 17.04 | 43.98 | 126.49 | 360 条射线；**含 `ranges` 列表拷贝**（尾部明显长） |
| `nearest_obstacle_distance()` | 20000 | 6.54 | 9.52 | 23.06 | 加锁扫描 + 角度过滤 |
| `move_to_joint_positions`（原地） | 15 | 19675 | 20771 | 20771 | 纯动作链路（后端 1 拍） |
| `move_to_joint_positions`（0.02 rad） | 15 | 39753 | 40390 | 40390 | 含 mock 的运动时间（后端 2 拍） |
| GIL：纯 Python 循环吞吐比 | — | 1.08 | — | — | spin 在转 ÷ 无 SDK（1.0 = 无干扰） |

**复现性**：同机连跑两轮，p50 偏差 ≤1 µs（动作 ≤0.3 ms）；p99 抖得厉害（`laser_scan` 两轮是 52 与 126 µs），
机器状态本身也会漂（GIL 基线 8.4–9.4M 次/0.5 s，约 10%）。⇒ **读数量级与构成，别读末位数字。**

## 怎么读这些数（**别用错**）

**① 缓存读 ≈ 免费。** 地板 3.06 µs 里主要是 pybind 边界与属性访问；`status()` 只比它多 1.2 µs（加锁 + 投影）。
⇒ agent/MCP 侧**可以放心高频轮询**：50 Hz 读状态也只占约 0.02% 的时间，"读缓存不阻塞"在数字上成立。

**② `laser_scan()` 的 17 µs 全花在拷贝上**，它是唯一"贵"的一项：每次读都要把 360 个 float 拷成 Python list
（长尾也在这里 —— p99 上百微秒）。绑定里 **image / point_cloud 刻意不拷 `data`**（几百 KB~几 MB 拷不起），
所以那两项反而便宜，要像素自己 `bytes(msg)`。

**③ 动作那 20 ms / 40 ms 不是 SDK 的耗时。** 它们是 mock 的**控制周期 20 ms（50 Hz）的整数倍**：
原地不动 = 1 拍就判"到了"；走 0.02 rad（`max_velocity=1`）≈ 走 1 拍 + 判 1 拍。分布也印证这点（p99 只比 p50 高 1 ms，量化得很干净）。
⇒ 说"SDK 的动作开销是 20 ms"是**错的**；这条数只能说明"SDK 的动作链路（发出→受理→收结果）短于后端一拍"。
真后端的耗时是**规划/执行**时间（Nav2 一条导航、MoveIt 一次规划），那是另一个量级、另一份账。

**④ GIL：spin 不会掐住 Python（比值 1.08）。** 这不是巧合，是绑定里两处刻意的设计：
`spin()/spin_some()` 用 `py::call_guard<py::gil_scoped_release>()`，所有会阻塞的调用（`wait_for_*`、动作、`server_available`）都用 `withoutGil()` 包着。
⇒ **这条是 MCP 那侧用 `asyncio.to_thread` 的前提**：GIL 不放开的话，"多个工具并发调用"会全部串在一个 GIL 上，多线程纯属自欺。
（代价：GIL 释放/重取本身有开销，所以**廉价缓存读刻意不放开** —— 几微秒的调用不值得为它付这个。）

## MCP 工具往返（agent 真正感受到的那层）

上面是"直连 SDK"的数。但 agent 走的是 **MCP**：客户端 → stdio JSON-RPC → 服务端事件循环 →
`to_thread` 跳线 → SDK → 后端。用 `./scripts/run_bench_mcp.sh` 量（Walle 连的就是这条路）：

| MCP 工具 | n | p50 | p95 | p99 | 说明 |
|---|---|---|---|---|---|
| `get_status` | 200 | 1.83 | 2.97 | 4.32 | 毫秒；两轮跑下来 p50 都在 1.7–1.9 |
| `get_pose` | 200 | 1.88 | 3.52 | 4.27 | |
| `joint_states` | 200 | 1.74 | 2.59 | 3.41 | |
| `scan_summary` | 200 | 1.83 | 2.85 | 3.98 | |

**三个结论**：

1. **这一层约 1.8 ms/次**，而直连 SDK 是 4.3 µs ⇒ MCP 封装让它慢约 **400 倍**。这倍数看着吓人，但要放在尺度上看：
   1.8 ms 相对 LLM 一次推理（秒级）只占约 **0.1%** ⇒ **工具层不是瓶颈，模型才是**。优先级因此很清楚。
2. **四个工具的数几乎一样**（哪怕底下的 SDK 调用是 4.3 µs 与 17 µs 的差别）—— 说明这 1.8 ms 是**常数开销**
   （stdio 往返 + JSON 编解码 + 事件循环 + 线程跳），不随工作量变。⇒ **少调一次工具，比把每次调用优化快一倍更值钱。**
3. 测的这段**含**协议、事件循环、`to_thread` 跳线与 SDK；**不含** LLM 推理，也不含 Walle 自己的工具循环/审批规则。
   动作类工具（`navigate_to`/`home`）没单列：它们由后端节拍主导（见上文 ③）。

## 不包含什么

- **不含** Nav2 / MoveIt / 真硬件的规划与执行时间；也不含 DDS 跨机传输（本机回环）。
- **不测 C++ 内部微基准**：调用方（agent/MCP）感受到的是"从 Python 调进来"这一整段，把 C++ 内部再切细对判断没帮助。
- 单线程数字：并发/扩缩容（多线程各自读缓存会不会被 GIL 串住）**没测**，如需要另开一轮。

## 复现

```bash
./scripts/run_bench.sh                 # 起 mock → 测 → 自动收摊
./scripts/run_bench.sh --json log/bench.json --n 50000 --moves 30
./scripts/run_bench_mcp.sh --n 200     # MCP 工具往返（用 robot_sdk_mcp 的 venv python）
```

- 起跑前会**先查有没有游离的机器人**（第二个同名服务端会让数字全成垃圾，见 `src/robot_sdk_tests/README.md`）。
- **刻意不进 CI**：缓存读与动作都按时序判定，进了 CI 只会多一条 flake；它是"面试/回归时手动按一下"的工具。
